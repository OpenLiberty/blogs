= WebSphere Liberty と Open Liberty がクラウドネイティブ Java アプリケーションに最適である 6 つの理由
Graham Charters <https://github.com/gcharters>

//Blank line here is necessary before starting the body of the post.

Liberty は、高速でモジュール化されたクラウド ネイティブの Java ランタイムです。link:https://www.ibm.com/products/cloud-pak-for-applications/liberty[IBM WebSphere Liberty] は、開発者にとって使いやすく、軽量で俊敏な Java ランタイムに対する需要の高まりに応えて 2012 年に作成されました。2017 年に、IBM は WebSphere Liberty のソース コードをlink:https://openliberty.io/[Open Liberty]プロジェクトとしてリリースし、現在では WebSphere Liberty と Open Liberty の両方がこのプロジェクトから構築されています。

Open Liberty は、新しいクラウドネイティブ アプリケーションに必要なものを提供し、IBM からの商用サポートのオプションも用意されています。WebSphere Liberty は、Open Liberty のすべての機能に加えて、既存のエンタープライズ アプリケーションの最新化や仮想マシンでの大規模クラスターの管理を容易にする追加機能を提供します。WebSphere Liberty、Open Liberty、またはその両方の組み合わせた環境も構築できます。

ここから！！！

Liberty は、従来のアプリケーション サーバー ランタイムと比較して、アプリケーションの開発と展開を大幅に簡素化します。Liberty は構成が簡単で、34 MB 未満から Jakarta EE/Java EE の完全なサポートまで、適切なサイズの展開を作成できます。Liberty のゼロ移行アーキテクチャにより、バージョン間の移行の課題が解消され、自動チューニングによりコストのかかるチューニング サイクルなしで最適なパフォーマンスが得られ、定期的なリリース サイクルにより継続的な配信が可能になります。

これらの特徴に加えて、Liberty は、第一級のコンテナ サポート、Kubernetes の最適化、MicroProfile や Jakarta EE などのクラウド ネイティブ API の使用も提供します。これらすべての特徴により、Liberty は新しいクラウド ネイティブのマイクロサービス ベースのアプリケーションに最適な選択肢となります。Liberty は古い API もサポートしているため、必要に応じて、どこまでモダナイゼーションを進めたいかに関係なく、既存のワークロードを実行するのにも最適です。

それでは、Liberty と他のランタイムの違いについてもう少し詳しく見てみましょう。具体的には、Liberty がクラウドネイティブ Java マイクロサービスとアプリケーションに最適な選択肢である主な 6 つの理由を探ります。

== 理由1: モノリス、マクロサービス、マイクロサービス

組織には、組織や各チームの規模と構造、必要な更新の頻度、柔軟性と俊敏性のニーズなど、さまざまな要因に応じて異なるアーキテクチャ ニーズがあります。幅広いアーキテクチャ サポートに対応するランタイムを選択すると、時間の経過とともに変化する可能性のある Java アプリケーションのアーキテクチャ要件に応じてランタイムを変更しなければならないというフラストレーションを回避できます。

Liberty は、この幅広いアーキテクチャ サポートを提供します。Liberty は、本質的にモジュール化されたクラウド ネイティブ ランタイムであり、オンプレミス、選択したクラウド、Kubernetes、Red Hat OpenShift のいずれであっても、VM 内の大規模なエンタープライズ モノリスからコンテナー上の小規模なマイクロサービスまで、さまざまなアーキテクチャ スタイルを実装するさまざまなミッション クリティカルなアプリケーションを実行できることが実証されています。

Liberty のこの利点の重要性を示す実際の顧客事例としては、PowerM が Liberty を使用してモロッコ政府のミッションクリティカルな政府サービスを強化した事例や、Primeur が Liberty を使用してさまざまなアーキテクチャ スタイルのアプリケーションをサポートした事例が挙げられます。

== 理由２： APIサポートの幅広さ

幅広い標準 API をサポートすることで、アプリケーションの柔軟性と移植性が確保され、ベンダー ロックインによって生じるフラストレーションを回避するのに役立ちます。

Liberty では、開発者が活用できる次のような幅広い API セットが有効になります。

業界標準（MicroProfile、Jakarta EE など）
オープンソースフレームワーク（例：Spring Boot）
古い API を使用すると、古いアプリケーションを変更せずに簡単に実行できます (例: Java EE 6、7、8)
実際、Liberty に携わる多くのアーキテクトやエンジニアがこれらのオープン ソース標準、プロジェクト、コミュニティを運営および主導しており、Liberty はこれらの革新的な活動の最前線に立っています。

Liberty は幅広い API をサポートしていますが、Liberty のモジュール性により、アプリケーションに必要な API のみを組み込むだけで済み、クラウドへの展開に適した、可能な限り軽量で適切なサイズのイメージを作成できます。

この幅広い API サポートにより、Liberty は最新化の取り組みを最小限に抑えることができます。Liberty を使用すると、あらゆるアプリケーションで、既存の投資を利用して最新のモジュール式のハイブリッド クラウド アプリケーションを作成することも、新しいクラウド ネイティブの代替アプリケーションをゼロから構築することもできます。

スイスの大手医療保険プロバイダーであるSuva は、Liberty の API および OSS 標準サポートの利点を示す優れた例です。

== 理由３： 効率的な開発者ツール

ファーストクラスの開発者エクスペリエンスにより、開発者の生産性が向上します。新しいLiberty Tools は、Java の最も一般的な統合開発環境 (IDE) であるEclipse IDE、Visual Studio Code、およびIntelliJ IDEAと統合された、直感的で強力な開発者ツールです。Liberty Tools を使用すると、開発者は編集とコードの支援を受けることができ、MicroProfile および Jakarta EE オープン標準を使用するクラウドネイティブ アプリケーションを効率的に開発、テスト、デバッグできます。

Liberty Tools では、これらの IDE から Liberty の開発モードを直接使用することもできます。これにより、実行中のサーバーで自動ホット リロードが提供されます。Liberty の開発モードを使用すると、開発者はローカル コンテナーまたはローカル サーバーでコードと構成の変更を迅速かつ簡単に実行してテストでき、IDE 内でテスト レポートを利用できます。これにより、コードまたは構成を変更するたびに完全に再構築して再デプロイする必要がなくなり、開発者が更新を開発してテストするのにかかる時間が大幅に短縮されます。最も人気のあるビルド ツール ( MavenおよびGradle ) との統合とコンテナー サポートにより、開発者は本番環境にできるだけ近い環境で開発とテストを行うことができます。

次のビデオでは、Liberty Tools が提供する機能と、それを統合開発環境 (IDE) である Visual Studio Code で使用する方法について、開発者向けに詳しく説明しています。

== 理由４：ゼロマイグレーション・ポリシーにより、最新の環境に容易に移行可能

セキュリティを強化したり、新機能を利用したりするために、アプリケーションが依存するテクノロジを最新バージョンに移行するには、多くの場合、アプリケーション コードや構成に大幅な変更が必要になります。これまで、このような移行はチームに不安を与えてきました。何ヶ月も前に計画する必要があり、完了するまでに何ヶ月、場合によっては何年もかかるからです。最新の状態を維持するだけでも、多大な投資が必要です。

Liberty の「ゼロ マイグレーション」アーキテクチャにより、アプリケーションのコードや構成を変更することなく、わずか数分 (または数秒) で最新の Liberty バージョンに簡単に移行できます。ゼロ マイグレーションと Liberty の継続的デリバリーを組み合わせると、開発者は 4 週間ごとに更新でき、最新のセキュリティ修正プログラムと拡張機能を利用できるようになります。

IBM ビジネス パートナーである RedBridge とのクライアント ケース スタディでは、ヨーロッパの大手銀行にとって当社のゼロ移行アーキテクチャが実現した重要性と大きな利点が紹介されています。

次のビデオでは、コードや構成の変更なしに 900 を超える修正を加えて更新されるデモ アプリケーションを通じて、ゼロ マイグレーションが実際に有益である理由を説明します。


== 理由５：  アプリケーションのパフォーマンスを向上してコストを削減

クラウドおよびサーバーレス アーキテクチャ スタイルにより、変動するワークロード需要に応じてアプリケーションを迅速に動的にスケーリングする必要が生じています。ワークロード需要が低い場合、運用コストを削減するためにアプリケーションをスケールダウンする必要があります。これは「スケール ツー ゼロ」と呼ばれます。その後、需要が再び増加すると、アプリケーションとランタイムのインスタンスをさらにプロビジョニングする必要があります。エンド ユーザーが応答時間の遅延を経験しないように、このスケールアップは迅速に行う必要があります。したがって、ランタイムの起動時間は、アプリケーションのパフォーマンスとコストの最適化に重要な役割を果たす可能性があります。

この記事のすべての比較グラフは、次の構成で実行されました。

Intel 上の RHEL 8.7
インテル Xeon Gold 6338 @ 2.00 GHz
2 つの CPU と 1 GB の RAM
各サーバーインスタンスには、Dockerイメージで配布されているバージョンであるJDK 11が使用されました。
JVM は長年にわたり、アプリケーションの高スループットのために最適化されており、最初のリクエストにできるだけ早く応答することよりも、JVM インスタンスの起動時に多くの作業を行うことに重点を置いています。ただし、急速な動的スケーリングには、1 秒未満の起動時間が必要です。Linuxのチェックポイント/リストア テクノロジに基づくLiberty の InstantOn 機能を使用すると、スループット、メモリ、開発と本番のパリティ、または Java 言語機能 ( GraalVM ネイティブ コンパイルとはまったく異なります) を犠牲にすることなく、アプリケーションを数ミリ秒で起動できます。

次のグラフは、InstantOn を使用するとアプリケーションの起動が通常最大 10 倍高速化され、アプリケーションが急速にスケールアップする一方で、アプリケーションが使用されていないときにはゼロにスケールアップできることを示しています。Liberty InstantOn の詳細については、この記事「妥協のないクラウドネイティブ Java アプリケーションの高速起動」を参照してください。

== 理由６： クラウドリソースを効率的に利用してコストを削減

クラウドでアプリケーションを実行する場合、ディスク上のアプリケーションのサイズ、使用するメモリの量、CPU 使用率によって、ビジネスにかかるクラウド コストが決まります。マイクロサービス アーキテクチャでは、サービスごとにランタイムのインスタンスを使用して、数十または数百のマイクロサービスを実行することが多くなるため、これらのマイクロサービスが可能な限り効率的であることが重要です。マイクロサービスを展開しない場合でも、モノリスなどの他のアーキテクチャでも、低コストでフットプリントの小さいランタイムのメリットを享受できます。

Liberty は小型でモジュール式なので、サービスに必要な機能だけを Liberty カーネルに追加するだけです。

次の表は、Open Liberty 23.0.0.5 (Java17) で実行されている 3 つの異なるアプリケーション タイプのディスクおよびメモリのサイズを示しています。

パッケージ	アプリケーションの種類	ディスク上のサイズ	メモリ
ジャカルタ EE 10 + MicroProfile 6.0	最新のクラウドネイティブモノリス	136MB	252MB
マイクロプロファイル 6.0	クラウドネイティブマイクロサービス	65MB	180MB
サーブレット 6.0	シンプルなウェブフレームワーク	34MB	102MB
メモリフットプリントとクラウド サービスのコストには明確な相関関係があります。たとえば、Azure Kubernetes Service の価格は、ノードのメモリ要件が 2 倍になると実質的に 2 倍になります。Liberty のメモリフットプリントの低さは、次の比較グラフで強調されています。


== ボーナス: 主要なクラウドへのデプロイが容易になります

Liberty は、 Azure、Red Hat OpenShift、AWS、IBM Cloudなど、すべての主要なクラウド (プライベート、パブリック、ハイブリッド) で容易にデプロイできるため、アプリケーションを柔軟にポータブルに実行することができます。

Liberty は、主要クラウドにデプロイできるだけでなく、仮想マシン、軽量化されたコンテナ、Open Liberty Operatorによる Kubernetes へのデプロイメント、クラウドネイティブのビルドパック、Red Hat OpenShift のSource-to-Image (S2I) ツールキット、プラットフォーム固有のアプローチの使用など、デプロイメントにおいて、さまざまなオプションを提供しています。

== 次のステップ

クラウドネイティブな環境への移行により、開発や運用において、新たに下記のような点を考慮する必要があります。

- クラウドネイティブAPIの必要性
- 高いスループットと低いリソース使用量を備えたランタイムの必要性
- 質の高いコンテナとKubernetesの統合の必要性
- 簡単かつ頻繁にアップグレードすることでセキュリティを維持できる必要性

本記事では、これらの新しい課題に対応している Liberty の 6 つの機能に焦点を当て、Liberty が理想的な選択肢である理由をご説明しています。Libertyは、「Open Liberty を使い始める」のページから、今すぐお試しいただけます。
