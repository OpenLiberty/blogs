[#mcp]
== MCP Server (mcp-1.0)

link:https://modelcontextprotocol.io/[Model Context Protocol (MCP)] は、AI アプリケーションが外部ソースからリアルタイムのデータとビジネス・ロジックにアクセスできるようにするオープン・スタンダードです。MCP Server の機能 (`mcp-1.0`) を使用すると、アプリケーション開発者はいくつかのアノテーションを追加するだけで、Liberty アプリケーションのツールとデータをエージェント型 AI ワークフローで利用できるように公開できます。

`mcp-1.0` 以前は、Liberty アプリケーションの既存の Java ビジネス・ロジックを AI エージェントに公開するための標準的な方法がありませんでした。接続したい AI ツールごとにカスタム統合を構築・維持する必要がありました。`mcp-1.0` では、既存の CDI メソッドに `@Tool` アノテーションを付けるだけで、Liberty が MCP プロトコル、ツール検出、セッション管理、セキュリティー、およびオブザーバビリティを自動的に処理します。ビジネス・ロジックを変更することなく、アプリケーションは MCP 互換の AI エージェントからすぐに利用可能になります。

入門ガイドと使用例の詳細については、link:{url-prefix}/blog/2026/08/25/mcp-tools.html[Liberty ビジネス・ロジックを AI ツールとして公開するブログ記事]および link:{url-prefix}/docs/latest/liberty-mcp-server.html[mcp-1.0 の機能ドキュメント]をご参照ください。

=== 26.0.0.9 の新機能

複数のベータ・リリースを経て、`mcp-1.0` が一般提供 (GA) されました。最後のベータ版 (`26.0.0.9-beta`) からの最も重要な変更点は、機能名が `mcpServer-1.0` から `mcp-1.0` に変更され、`server.xml` ファイルの設定要素が `<mcpServer>` から `<mcp>` に変更されたことです。`server.xml` ファイルを次のように更新してください:

[source,xml]
----
<featureManager>
    <feature>mcp-1.0</feature>
</featureManager>
<application location="my-app.war">
    <mcp path="/custom-mcp"/>
</application>
----

26.0.0.8-beta 以前のバージョンから移行する場合、コア API タイプも `io.openliberty.mcp.*` から `org.mcpjava.server.*` に移動しました。インポートの変更に関する詳細は、link:{url-prefix}/blog/2026/08/25/26.0.0.9-beta.html[26.0.0.9-beta のブログ記事]をご参照ください。

以下の機能は、この GA リリースの新機能であり、26.0.0.9-beta には含まれていませんでした:

* *DNS リバインディング攻撃への防御* — MCP Server がループバック・アドレスからのリクエストを受信した場合、MCP 仕様の要件に従って `Origin` ヘッダーを検証するようになりました。設定は不要です。
* *ツール・メソッドへの `@MetaField` サポート* — ツール・メソッドに `@MetaField` アノテーションを付けることで、`tools/list` レスポンスの `_meta` オブジェクトにデータを追加できます。
* *`@Tool` での `outputSchemaFrom`* — `structuredContent = true` の場合、メソッドの戻り値の型とは独立して、出力スキーマの生成に使用するクラスを指定できます。
* *サポートされていないアノテーションに対する警告* — `mcp-1.0` でサポートされていない MCP Java API アノテーション (`@Prompt`、`@Resource`、`@ResourceTemplate` など) をアプリケーションが使用している場合、Liberty が警告をログに記録するようになりました。アプリケーションは引き続き起動し、`@Tool` アノテーションが付いたメソッドは引き続き動作します。
* *OAuth 2.0 保護リソース・メタデータ (RFC 9720)* — `openidConnectClient` に `protectedResourceMetaDataEnabled="true"` が設定されている場合、Liberty は `/.well-known/oauth-protected-resource` で保護リソース・メタデータ・ドキュメントを提供します。これにより、MCP クライアントは MCP 認可フローに従って適切な認可サーバーを自動的に検出できます。

[#protected_resource_metadata]
== openidConnectClient の保護リソース・メタデータ

OAuth 2.0 保護リソース・メタデータ (RFC 9720) は、OAuth 2.0 で保護されたリソースに関するメタデータ (アクセスを許可できる認可サーバーへのリンクを含む) を提供します。

このリリースでは、`openidConnectClient-1.0` の機能を使用する Open Liberty サーバーで保護リソース・メタデータを有効にできます。保護リソース・メタデータは任意の `openidConnectClient` 設定で有効にできますが、主な使用例は MCP 認可フローをサポートするための `mcp-1.0` の機能との組み合わせです。このフローでは、MCP クライアントが保護リソース・メタデータを使用して認可サーバーを検出します。

`openidConnectClient` 設定に対して保護リソース・メタデータを有効にするには、`<protectedResourceMetadata>` 設定要素を追加してください:

[source,xml]
----
<openidConnectClient id="protected-resource-demo"
    clientId="protected-resource"
    clientSecret="..."
    jwkEndpointUrl="https://auth.example.com/oidc/endpoint/SampleProvider/jwk"
    tokenEndpointAuthMethod="basic"
    issuerIdentifier="https://auth.example.com/oidc/endpoint/SampleProvider"
    authFilterRef="mcpAuthFilter"
    inboundPropagation="required">
    <protectedResourceMetadata />
</openidConnectClient>
----

詳細については、link:{url-prefix}/docs/latest/reference/feature/openidConnectClient-1.0.html[OpenID Connect Client の機能ドキュメント]および link:{url-prefix}/docs/latest/reference/config/openidConnectClient.html[openidConnectClient 設定リファレンス]をご参照ください。


[#session_cache_prefix]
== 共有 JCache クラスター向けのカスタム・セッション・キャッシュ名プレフィックス

同じ JCache ベースのセッション・ストアを共有する複数の Liberty インスタンス (例えば、同じ Hazelcast または Infinispan クラスターを参照している Kubernetes または OpenShift 上の複数の Pod) を実行する場合、以前の Liberty は各インスタンスで同一のセッション・キャッシュ名を生成していました。キャッシュ名が同一であると、異なるインスタンスが同じキャッシュを競合して使用することになり、共有キャッシュのデプロイメントでセッション・データが破損するリスクがありました。

Open Liberty 26.0.0.9 では、`sessionCache-1.0` の機能の `httpSessionCache` 要素に新しい `cacheNamePrefix` 属性が追加されました。この属性は、共有キャッシュ・クラスターを使用する複数インスタンスの Liberty デプロイメントを運用するオペレーション・チームや管理者を対象としています。衝突を避けるために各インスタンスに個別のキャッシュ名前空間が必要な場合に使用してください。

以前は、Liberty が常に `com.ibm.ws.session.meta.XXX` または `com.ibm.ws.session.attr.XXX` という形式でセッション・キャッシュ名を生成しており、どの Liberty サーバーが作成したかを区別する方法がありませんでした。現在は、各 Liberty サーバーに固有のプレフィックスを設定できます。これにより、1 つの共有クラスターが名前空間の衝突なく複数の Liberty サーバーからのセッション・データを安全にホストできるようになります。プレフィックスが設定されていない場合は、従来のキャッシュ名が引き続き使用されます。

キャッシュ名プレフィックスを設定するには、`httpSessionCache` 設定に `cacheNamePrefix` 属性を追加してください:

[source,xml]
----
<!-- Instance 1 -->
<httpSessionCache cacheRef="InfinispanCacheManager" cacheNamePrefix="pod1_"/>
<!-- Instance 2 -->
<httpSessionCache cacheRef="InfinispanCacheManager" cacheNamePrefix="pod2_"/>
----

プレフィックスにより、各インスタンスに異なるキャッシュ名が付与されます (`pod1_com.ibm.ws.session.attr.default_host/myapp` および `pod2_com.ibm.ws.session.attr.default_host/myapp`)。プレフィックスがない場合、両方のインスタンスが同じ `com.ibm.ws.session.attr.default_host/myapp` というキャッシュ名を生成します。`cacheNamePrefix` 属性は、以下の用途に特に有用です:

* マルチテナント・デプロイメント
* 個別のキャッシュ名前空間が必要なブルーグリーン・デプロイメント
* Pod 固有のキャッシュ分離が必要な Kubernetes/OpenShift デプロイメント

セッション・キャッシングの設定に関する詳細については、link:{url-prefix}/docs/latest/reference/config/httpSessionCache.html[httpSessionCache リファレンス]ドキュメントをご参照ください。
