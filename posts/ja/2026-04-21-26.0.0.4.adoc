[#file_transfer]
=== 26.0.0.4 における File Transfer の変更
`restConnector-2.0` 機能によって提供される Liberty の FileService MBean に、追加の `blocklist` 属性が含まれるようになりました。この属性は、`server.xml` ファイル内の `<blockDir>` 構成要素によって設定されます。この属性のデフォルト値は `${server.output.dir}/resources/security` です。この動作変更により、デフォルトの FileTransfer アクセスが `${server.output.dir}/resources/security` に制限され、セキュリティー脆弱性 link:https://github.com/advisories/GHSA-c39w-6qgm-5cp7[CVE-2025-14915] が解決されます。

`${server.output.dir}/resources/security` への FileTransfer アクセスが必要な場合は、空の blocklist を設定することで元の動作を復元できます。

詳しくは、link:https://www.ibm.com/docs/en/was-liberty/nd?topic=manually-file-transfer[ドキュメント] を参照してください。

[#ltpa]
== デフォルトの LTPA キー・パスワードの削除

セキュリティー脆弱性 link:https://www.ibm.com/support/pages/node/7266845[CVE-2025-14917] を解決するために、デフォルトの LTPA キー・パスワードが削除されました。

以前は、`<ltpa />` 要素で `keysPassword` 属性が定義されていない場合、LTPA キーにはデフォルトのパスワードが使用されていました。この変更により、デフォルトのパスワードはサポートされなくなりました。

既存のサーバーでは、`server.xml` ファイルに LTPA キー・パスワードが構成されていない場合、`server.env` ファイル内の `keystore_password` が使用されます。この値により、`ltpa.keys` ファイル内の LTPA キーが再暗号化されます。LTPA キー自体には影響しません。`keystore_password` は、`server create` コマンドで `--no-password` オプションを使用しない限り、サーバー作成時に `server.env` ファイルに構成されます。

`server.xml` ファイルの `<ltpa />` 要素で `keysPassword` が定義されておらず、`server.env` ファイルで `keystore_password` も定義されていない場合、LTPA サービスは失敗します。
次のエラー・メッセージが表示されます:

[source,text]
----
CWWKS4118E: LTPA configuration error. A keysPassword attribute is not configured on the <ltpa /> element, the 'ltpa_keys_password' environment variable is not set, and the 'keystore_password' environment variable is not set.
----

以下の手順で、LTPA キー・パスワードが設定されていることを確認してください。

. `server.xml` ファイルの `<ltpa />` 要素に `keysPassword` 属性が指定されているか確認します（例: `<ltpa keysPassword="myKeysPassword" />`）。
* 指定されている場合、この更新の影響はなく、追加の対応は不要です。
* 指定されていない場合は、追加せずに次の手順に進みます。
. `server.env` ファイルに `keystore_password` 環境変数が存在するか確認します（例: `keystore_password=myKeystorePassword`）。
* 存在する場合、サーバーの起動時に、以前デフォルトの `keysPassword` で暗号化されていた LTPA キーを再暗号化するために `keystore_password` が使用されます。
* 存在しない場合は、次の手順に進みます。
. `server.env` ファイルに次の環境変数を追加します（ここでは、次のセクションで新規サーバー向けに説明する `ltpa_keys_password` ではなく、必ず `keystore_password` を使用してください）。
+
[source,properties]
----
keystore_password=your-desired-password
----
+
* `keystore_password` は、サーバーの起動時に、以前デフォルトの `keysPassword` で暗号化されていた LTPA キーを再暗号化するために使用されます。

新規サーバーでは、新しい `ltpa_keys_password` がサーバー作成時にランダムに生成されます。これは、`server create` コマンドで `--no-password` オプションを指定しない限り、`server.env` ファイルに保存されます。`<ltpa />` 要素に `keysPassword` 属性が定義されていない場合は、ランダムに生成された `ltpa_keys_password` が使用されます。

詳しくは、link:https://openliberty.io/docs/latest/reference/config/ltpa.html[LTPA] 構成要素を参照してください。


[#jwt]
== JOSE ヘッダーから JWT の署名および復号アルゴリズムを選択するサポート

JSON Web Token (JWT) は、さまざまな暗号署名アルゴリズムを使用して署名できます。このリリースでは、JWT Consumer、MicroProfile JWT、OpenID Connect Client、および Social Media Login 機能で、JOSE ヘッダーから JWT 署名アルゴリズムを選択することをサポートします。このサポートにより、トークン・ヘッダーに基づいて異なる署名アルゴリズムを使用できます。

以前は、`server.xml` ファイル内の各構成に対して、1 つの署名アルゴリズム（たとえば `RS256`）しか構成できませんでした。受信した JWT が異なるアルゴリズムで署名されている場合、検証は失敗していました。この更新により、JWT ヘッダーの署名アルゴリズムを検証に使用できるようになります。これにより、単一の構成内で異なる署名アルゴリズムを柔軟に使用できます。

=== 使用方法

ヘッダーからの署名アルゴリズム選択を有効にするには、`signatureAlgorithm` 属性を `FROM_HEADER` に設定し、必要に応じて `allowedSignatureAlgorithms` 属性を構成して許可するアルゴリズムを指定します。

`allowedSignatureAlgorithms` が構成されていない場合、デフォルトのリストには Open Liberty がサポートするすべての署名アルゴリズムが含まれます: `RS256, RS384, RS512, HS256, HS384, HS512, ES256, ES384`, および `ES512`。

非対称アルゴリズムとトラストストア設定で `FROM_HEADER` を使用する場合、自動選択のために公開鍵には対応するアルゴリズムの接頭辞（例: `RS256_keyalias`）を付ける必要があります。検証時に、サーバーは JWT ヘッダーで指定されたアルゴリズムで始まる別名をトラストストア内で検索します。アルゴリズム接頭辞付きの別名が見つからない場合、構成されていれば、クライアントは `trustedAlias` 属性（`jwtConsumer` の場合）または `trustAliasName` 属性（`openidConnectClient`、`oidcLogin`、`mpJwt` の場合）で指定された別名の使用にフォールバックします。

サポートされる要素にこれらの設定を適用する方法の例については、以下の `server.xml` ファイル構成を参照してください。

[source,xml]
----
<jwtConsumer
    signatureAlgorithm="FROM_HEADER"
    allowedSignatureAlgorithms="RS256, ES384, HS512" 
    ...
/>

<mpJwt
    signatureAlgorithm="FROM_HEADER"
    allowedSignatureAlgorithms="RS256, ES384, HS512"
    ... 
/>

<openidConnectClient
    signatureAlgorithm="FROM_HEADER"
    allowedSignatureAlgorithms="RS256, ES384, HS512" 
    ... 
/>

<oidcLogin
    signatureAlgorithm="FROM_HEADER"
    allowedSignatureAlgorithms="RS256, ES384, HS512" 
    ... 
/>
----

=== Java 26 のサポート
Java 26 は最近の Java リリースであり、以前のバージョンに比べて新機能と機能強化が導入されているため、確認する価値があります。このリリースは長期サポート (LTS) リリースではありません。

link:https://openjdk.org/projects/jdk/26/[Java 26] には 10 個の新機能 (JEP) があります。5 つはテスト機能で、5 つは正式提供された機能です。

*テスト機能:*

* 524: link:https://openjdk.org/jeps/524[暗号オブジェクトの PEM エンコーディング (第 2 プレビュー)]
* 525: link:https://openjdk.org/jeps/525[構造化並行性 (第 6 プレビュー)]
* 526: link:https://openjdk.org/jeps/526[遅延定数 (第 2 プレビュー)]
* 529: link:https://openjdk.org/jeps/529[Vector API (第 11 インキュベーター)]
* 530: link:https://openjdk.org/jeps/530[パターン、instanceof、および switch におけるプリミティブ型 (第 4 プレビュー)]

*正式提供された機能:*

* 500: link:https://openjdk.org/jeps/500[final を真に final にするための準備]
* 504: link:https://openjdk.org/jeps/504[Applet API の削除]
* 516: link:https://openjdk.org/jeps/516[Any GC による Ahead-of-Time オブジェクト・キャッシング]
* 517: link:https://openjdk.org/jeps/517[HTTP Client API の HTTP/3]
* 522: link:https://openjdk.org/jeps/522[G1 GC: 同期の削減によるスループットの改善]

Java 26 の新しい変更である JEP 500（「final を真に final にするための準備」）では、ディープ・リフレクションを使用した final フィールドの変更を制限することで、final フィールドの真の不変性の適用が始まります。
Java 26 では、このような変更は引き続き機能しますが、デフォルトで実行時警告がトリガーされるため、開発者はより厳格な適用に備えることができます。
将来のリリースでは代わりに例外がスローされる可能性が高く、final は真に変更不可能になります。

開発者は、JVM フラグ（たとえば `--illegal-final-field-mutation=deny`）を使用することで、このより厳格な動作を早期に有効にし、問題をより早く検出できます。
この変更により、プログラムの正確性、セキュリティー、および JVM の最適化が向上します。

これらの変更を今すぐ活用して、アプリケーションやマイクロサービスが Java 26 上でどのように動作するかを評価する時間をより多く確保してください。

今すぐ、最新リリースの link:https://developer.ibm.com/languages/java/semeru-runtimes/downloads/[IBM Semeru Runtime 26] または link:https://adoptium.net/temurin/releases/?version=26[Temurin 26] をダウンロードし、その後 Open Liberty link:{url-prefix}/start/#runtime_releases[26.0.0.4] をダウンロードしてインストールすることで開始できます。Liberty サーバーの link:{url-prefix}/docs/latest/reference/config/server-configuration-overview.html#server-env[server.env] ファイルで `JAVA_HOME` を Java 26 のインストール・ディレクトリーに設定し、テストを開始してください。

Java 26 の詳細については、Java 26 の link:https://jdk.java.net/26/release-notes[リリース・ノート・ページ] および link:https://docs.oracle.com/en/java/javase/26/docs/api/index.html[API Javadoc ページ] を参照してください。

== displayCustomizedExceptionText プロパティー
このリリースでは、`displayCustomizedExceptionText` 構成に関するドキュメントとテストが追加されました。これにより、ユーザーは Liberty のデフォルトのエラー・メッセージ（SRVE0218E: Forbidden や SRVE0232E: An exception occurred など）を、より明確なユーザー定義メッセージで上書きできます。

この機能は、単純な `server.xml` ファイル構成によって有効になります。そこでは、カスタム・メッセージを特定の HTTP ステータス・コード（`403` および `500`）にマッピングできます。

テストにより、これらのカスタム・メッセージがサポートされるすべてのプラットフォームで Liberty のデフォルトを正しく置き換え、構成されたテキストがすべてのシナリオで一貫して返されることが確認されます。

[source,xml]
----
<webContainer displaycustomizedexceptiontext="Custom error message"/>
