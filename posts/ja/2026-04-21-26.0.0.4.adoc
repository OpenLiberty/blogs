[#file_transfer]
== `FileService` MBean にブロックリストを追加
Liberty の `restConnector-2.0` の機能が提供する `FileService` MBean に、`blocklist` 属性が追加されました。この属性は、`server.xml` ファイルの `<blockDir>` 構成要素によって設定されます。この属性のデフォルト値は `${server.output.dir}/resources/security` です。この拡張により、デフォルトで `${server.output.dir}/resources/security` へのファイル転送アクセスを制限することで、セキュリティー脆弱性 link:https://github.com/advisories/GHSA-c39w-6qgm-5cp7[CVE-2025-14915] が解決されます。

`${server.output.dir}/resources/security` への FileTransfer アクセスが必要な場合は、空のブロックリストを設定することで元の動作を復元できます。

詳細については、link:https://www.ibm.com/docs/en/was-liberty/nd?topic=manually-file-transfer[ドキュメント]を参照してください。

[#ltpa]
== デフォルトの LTPA 鍵パスワードの削除

セキュリティー脆弱性 link:https://www.ibm.com/support/pages/node/7266845[CVE-2025-14917] を解決するために、デフォルトの LTPA 鍵パスワードが削除されました。

これまでは、`<ltpa />` 要素で `keysPassword` 属性が定義されていない場合、LTPA 鍵に対してデフォルトのパスワードが使用されていました。この変更により、`keysPassword` 属性が設定されていない場合でも、デフォルトのパスワードは使用されなくなります。

既存のサーバーでは、LTPA 鍵パスワードが `server.xml` ファイルで設定されていない場合、`server.env` ファイル内の `keystore_password` が使用されます。この値により、`ltpa.keys` ファイル内の LTPA 鍵が再暗号化されます。LTPA 鍵そのものには影響ありません。`keystore_password` は、`server create` コマンドで `--no-password` オプションを使用しない限り、サーバー作成時に `server.env` ファイルに設定されます。

`server.xml` ファイルの `<ltpa />` 要素で `keysPassword` が定義されておらず、`server.env` ファイルで `keystore_password` も定義されていない場合、LTPA サービスは失敗します。
次のエラー・メッセージが表示されます。

[source,text]
----
CWWKS4118E: LTPA configuration error. A keysPassword attribute is not configured on the <ltpa /> element, the 'ltpa_keys_password' environment variable is not set, and the 'keystore_password' environment variable is not set.
----

LTPA 鍵パスワードが設定されていることを確認するには、次の手順を実行してください。

. `server.xml` ファイルの `<ltpa />` 要素に `keysPassword` 属性が指定されているかどうかを確認します（例: `<ltpa keysPassword="myKeysPassword" />`）。
* 指定されている場合、この更新の影響はなく、追加の対応は不要です。
* 指定されていない場合は、*追加せずに* 次のステップに進んでください。
. `server.env` ファイルに `keystore_password` 環境変数が存在するかどうかを確認します（例: `keystore_password=myKeystorePassword`）。
* 存在する場合、サーバーの起動時に `keystore_password` を使用して、以前はデフォルトの `keysPassword` で暗号化されていた LTPA 鍵を再暗号化します。
* 存在しない場合は、次のステップに進んでください。
. `server.env` ファイルに次の環境変数を追加します（新規サーバー向けに次のセクションで説明する `ltpa_keys_password` では*なく*、ここでは `keystore_password` を使用してください）。
+
[source,properties]
----
keystore_password=your-desired-password
----
+
* サーバーの起動時に `keystore_password` を使用して、以前はデフォルトの `keysPassword` で暗号化されていた LTPA 鍵を再暗号化します。

新規サーバーでは、サーバー作成時に `ltpa_keys_password` の値がランダムに生成されます。この値は、`server create` コマンドで `--no-password` オプションを指定しない限り、`server.env` ファイルに保存されます。`<ltpa />` 要素に `keysPassword` 属性が定義されていない場合は、ランダムに生成された `ltpa_keys_password` が使用されます。

詳細については、link:https://openliberty.io/docs/latest/reference/config/ltpa.html[LTPA] 構成要素を参照してください。


[#jwt]
== JOSE ヘッダーから JWT の署名アルゴリズムと復号アルゴリズムを選択するサポート

JSON Web Token (JWT) は、さまざまな暗号署名アルゴリズムを使用して署名できます。このリリースでは、JWT Consumer、MicroProfile JWT、OpenID Connect Client、および Social Media Login の機能で、JOSE ヘッダーから JWT の署名アルゴリズムを選択することをサポートします。このサポートにより、トークン・ヘッダーに基づいて異なる署名アルゴリズムを使用できるようになります。

これまでは、`server.xml` ファイル内の各構成に対して、単一の署名アルゴリズム (たとえば `RS256`) しか設定できませんでした。受信した JWT が異なるアルゴリズムで署名されている場合、検証は失敗していました。この更新により、JWT ヘッダーの署名アルゴリズムを検証に使用できるようになります。これにより、単一の構成内で異なる署名アルゴリズムを使用する柔軟性が得られます。

=== 使用方法

ヘッダーからの署名アルゴリズム選択を有効にするには、`signatureAlgorithm` 属性を `FROM_HEADER` に設定し、必要に応じて `allowedSignatureAlgorithms` 属性を構成して、許可するアルゴリズムを指定します。

`allowedSignatureAlgorithms` が構成されていない場合、デフォルトのリストには Open Liberty がサポートするすべての署名アルゴリズム (`RS256, RS384, RS512, HS256, HS384, HS512, ES256, ES384, ES512`) が含まれます。

非対称アルゴリズムとトラストストア構成で `FROM_HEADER` を使用する場合、対応する公開鍵のエイリアスには、対応するアルゴリズムのプレフィックスを付ける必要があります (例: `RS256_keyalias`)。エイリアス名の残りの部分は、署名アルゴリズム文字列で始まっていれば任意です。検証時に、サーバーは JWT のヘッダーで指定されたアルゴリズムで始まるエイリアスをトラストストアから検索します。アルゴリズムのプレフィックス付きエイリアスが見つからない場合、構成されていれば、クライアントは `trustedAlias` 属性 (`jwtConsumer` の場合) または `trustAliasName` 属性 (`openidConnectClient`、`oidcLogin`、`mpJwt` の場合) で指定されたエイリアスの使用にフォールバックします。トラストストア内に署名アルゴリズムのプレフィックスを持つエイリアスが複数存在する場合、Liberty は最初に見つかったものを使用します。

サポートされている要素にこれらの設定を適用する方法の例については、次の `server.xml` ファイルの構成を参照してください。

[source,xml]
----
<jwtConsumer
    signatureAlgorithm="FROM_HEADER"
    allowedSignatureAlgorithms="RS256, ES384, HS512" 
    ...
/>

<mpJwt
    signatureAlgorithm="FROM_HEADER"
    allowedSignatureAlgorithms="RS256, ES384, HS512"
    ... 
/>

<openidConnectClient
    signatureAlgorithm="FROM_HEADER"
    allowedSignatureAlgorithms="RS256, ES384, HS512" 
    ... 
/>

<oidcLogin
    signatureAlgorithm="FROM_HEADER"
    allowedSignatureAlgorithms="RS256, ES384, HS512" 
    ... 
/>
----

== Java 26 のサポート
Java 26 は、以前のバージョンと比べて確認しておくと有用な新機能と拡張を導入した最新の Java リリースです。このリリースは長期サポート (LTS) リリースではありません。

link:https://openjdk.org/projects/jdk/26/[Java 26] には、10 個の新機能 (JEP) があります。そのうち 5 個はテスト機能で、5 個は正式に提供された機能です。

*テスト機能:*

* 524: link:https://openjdk.org/jeps/524[PEM Encodings of Cryptographic Objects (Second Preview)]
* 525: link:https://openjdk.org/jeps/525[Structured Concurrency (Sixth Preview)]
* 526: link:https://openjdk.org/jeps/526[Lazy Constants (Second Preview)]
* 529: link:https://openjdk.org/jeps/529[Vector API (Eleventh Incubator)]
* 530: link:https://openjdk.org/jeps/530[Primitive Types in Patterns, instanceof, and switch (Fourth Preview)]

*正式提供された機能:*

* 500: link:https://openjdk.org/jeps/500[Prepare to Make Final Mean Final]
* 504: link:https://openjdk.org/jeps/504[Remove the Applet API]
* 516: link:https://openjdk.org/jeps/516[Ahead-of-Time Object Caching with Any GC]
* 517: link:https://openjdk.org/jeps/517[HTTP/3 for the HTTP Client API]
* 522: link:https://openjdk.org/jeps/522[G1 GC: Improve Throughput by Reducing Synchronization]

Java 26 における新たな変更である JEP 500 ("Prepare to Make Final Mean Final") では、ディープ・リフレクションを使用した final フィールドの変更を制限することで、final フィールドの真の不変性の適用が始まります。
Java 26 では、このような変更は引き続き動作しますが、デフォルトで実行時警告が出力されるため、開発者はより厳格な適用に備えることができます。
将来のリリースでは、代わりに例外がスローされる可能性が高くなり、final は真に変更不能になります。

開発者は、JVM フラグ (たとえば `--illegal-final-field-mutation=deny`) を使用することで、このより厳格な動作を早期に有効化し、問題をより早く検出できます。
この変更により、プログラムの正確性、セキュリティー、および JVM の最適化が向上します。

今のうちにこれらの変更を活用して、アプリケーションやマイクロサービスが Java 26 上でどのように動作するかを評価するための時間をより多く確保してください。

まずは、link:https://developer.ibm.com/languages/java/semeru-runtimes/downloads/[IBM Semeru Runtime 26] または link:https://adoptium.net/temurin/releases/?version=26[Temurin 26] の最新リリースをダウンロードし、その後 Open Liberty link:{url-prefix}/start/#runtime_releases[26.0.0.4] をダウンロードしてインストールしてください。Liberty サーバーの link:{url-prefix}/docs/latest/reference/config/server-configuration-overview.html#server-env[server.env] ファイルで `JAVA_HOME` を Java 26 のインストール・ディレクトリーに設定し、テストを開始できます。

Java 26 の詳細については、Java 26 の link:https://jdk.java.net/26/release-notes[リリース・ノート・ページ]および link:https://docs.oracle.com/en/java/javase/26/docs/api/index.html[API Javadoc ページ]を参照してください。

== Web Container の `displayCustomizedExceptionText` プロパティーに関するドキュメント
このリリースでは、`displayCustomizedExceptionText` 属性に関するドキュメントが `<webContainer>` 構成に追加されました。この属性により、ユーザーは Liberty のデフォルト・エラー・メッセージ (SRVE0218E: Forbidden や SRVE0232E: An exception occurred など) を、より分かりやすいユーザー定義メッセージで上書きできます。

この機能は、シンプルな `server.xml` ファイル構成によって有効化され、HTTP ステータス・コード (`403` および `500`) ごとにカスタム・メッセージをマッピングできます。

テストにより、これらのカスタム・メッセージがサポート対象のすべてのプラットフォームで Liberty のデフォルトを正しく置き換えることが確認されており、構成したテキストがあらゆるシナリオで一貫して返されることが保証されます。

[source,xml]
----
<webContainer displayCustomizedExceptionText="Custom error message"/>
