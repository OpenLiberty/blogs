= Building Better APIs: Documenting APIs in Open Liberty using mpOpenAPI
Sweetty P Devassy <https://github.com/sweettypdevassy>
:imagesdir: /
:url-prefix:
:url-about: /

In 2012, Twitter made significant changes to its API policies and access rules, tightening control over how third-party developers could interact with its platform. These changes affected many apps that relied on Twitter's API for services like tweet posting, timeline retrieval, and user authentication. However, due to a lack of proper API documentation, several third-party apps using Twitter’s API were unaware of these changes, leading to overnight crashes. This incident, along with similar issues across other platforms, acted as a wake-up call for the industry to standardise API documentation. 

With evolving technology, we are building a huge number of highly complicated APIs. Documenting these APIs requires effort and is often seen as a tedious task. Furthermore, complex APIs make documentation even more challenging. In reality, API documentation serves as a means of sharing up-to-date information between development teams. This crucial aspect later led to the development of Swagger and later OpenAPI specification. So, let's dive into the OpenAPI specification and explore how you can use it in your Open Liberty project with the mpOpenAPI library. 

== What is OpenAPI?  

*OpenAPI* is a *standardised specification* for describing *RESTful APIs* in a machine-readable format (JSON or YAML). It allows developers to *define, document, and share API structures* in a way that is both human-readable and programmatically useful. At its core, an OpenAPI definition includes:  

* *Info* – API title, version, description  

* *Servers* – Base URLs of the API  

* *Paths* – Endpoints (/users, /orders)  

* *Methods* – GET, POST, PUT, DELETE  

* *Parameters* – Query, path, header, or body inputs  

* *Responses* – Expected status codes and return data  

* *Security* – Authentication methods (OAuth, API keys, etc.)  

Swagger UI, developed by SmartBear Software, allows developers to visualize API documentation and test APIs interactively. 

== mpOpenAPI and Open Liberty  

For *Open Liberty developers, mpOpenAPI* library provides the integration to add the OpenAPI specification to Open Liberty. Integrating *mpOpenAPI* is crucial as it *automatically generates OpenAPI-compliant documentation* for JAX-RS services, eliminating the need for additional manual effort. Developers are now able to maintain *consistent, accurate, and up-to-date API documentation* effortlessly. Additionally, combining *mpOpenAPI with Swagger UI* enhances the developer and user experience by providing *interactive API documentation*, allowing users to visualise endpoints, test API calls, and understand request/response structures in a more intuitive way. This removes the need for manually written API documentation, reducing maintenance overhead and minimising the risk of outdated or inconsistent documentation. *mpOpenAPI streamlines API development* in Open Liberty, making it easier for teams to build, expose, and manage RESTful services efficiently.  

== Adding mpOpenAPI to Open Liberty 

To add OpenAPI to Open Liberty, we need to use MicroProfile and enable the mpOpenAPI feature. 

1 . Add MicroProfile dependency in `pom.xml`
[source, xml]
----
<dependency> 
  <groupId>org.eclipse.microprofile</groupId> 
  <artifactId>microprofile</artifactId> 
  <version>7.0</version> 
  <type>pom</type> 
  <scope>provided</scope> 
</dependency> 
----

2 . Update `server.xml` in `liberty/config` to enable mpOpenAPI: 
[source, xml]
----
<featureManager> 
    <feature>jakartaee-10.0</feature> 
    <feature>mpOpenAPI-4.0</feature> 
</featureManager>
----
3 . Create an Endpoints.java file, 

* This is where you will define your API endpoints using OpenAPI annotations. 

* The full source code for this example is available on GitHub: link:https://github.com/sweettypdevassy/openAPI-blog[GitHub Repository.] 

4 .  Run the project using Maven: `mvn liberty:dev`

5 . Test using Swagger UI: 

* Open: http://localhost:9081/openapi/ui/

== OpenAPI Annotations 

mpOpenAPI provides the following annotations:

[.img_border_light]
image::img/blog/OPENAPI-2.png[OpenAPI Annotations ,width=70%,align="center"] 

Below is an example of using MicroProfile OpenAPI annotations to define an API, its metadata, security, and operations. 

*1 . API Metadata Definitions*

* *`@OpenAPIDefinition`* - Defines metadata for the entire API.

* *`@Info`* - Provides metadata such as title, description, version, and contact details.  

* *`@Server`* - Specifies one or more servers where the API is hosted.  

* *`@Tag`* - Defines logical groupings of endpoints.  

* *`@SecurityRequirement`* - Enforces security (e.g., JWT authentication) for API endpoints.  

[source,  java]
----
@OpenAPIDefinition( 
    info = @Info( 
        title = "Blog API", 
        version = "1.0", 
        description = "This is an example API using MicroProfile OpenAPI", 
        contact = @Contact(name = "Sweetty", email = "sweetty@gmail.com"), 
        license = @License(name = "Apache 2.0", url = "https://apache.org/licenses/LICENSE-2.0.html") 
    ), 
    servers = @Server(url = "http://localhost:9081/openapi-demo", description = "Localhost Server"), 
    tags = { 
        @Tag(name = "Blog", description = "Operations related to blog management") 
    }, 
    security = @SecurityRequirement(name = "jwtAuth") 
) 
----
[.img_border_light]
image::img/blog/OPENAPI-3.png[API Metadata Definitions ,width=70%,align="center"] 

*2 . Security Definitions*  

* *`@SecurityScheme`* - Defines authentication for the API.  

* *`@SecuritySchemes`*- Specifies multiple security schemes if needed.  

[source,  java]
----
@SecuritySchemes({ 
    @SecurityScheme( 
        securitySchemeName = "jwtAuth", 
        description = "JWT Authentication", 
        type = SecuritySchemeType.HTTP, 
        scheme = "bearer", 
        bearerFormat = "JWT" 
    ) 
}) 
----
[.img_border_light]
image::img/blog/OPENAPI-4.png[Security Definitions ,width=70%,align="center"] 
*3 . API Operations*

* *`@Operation`* - Describes an API operation.  

* *`@APIResponse`* - Defines possible responses for an operation.  

* *`@ApiResponses`* - Groups multiple @APIResponse annotations.  

* *`@Content`* - Specifies the media type and structure of request/response bodies.  

* *`@Schema`* - Defines the properties of a model used in API requests and responses.

[source,  java]
----
@Operation(summary = "Get User by ID", description = "Returns the user details for a given ID") 
    @APIResponses({ 
    @APIResponse(responseCode = "200", description = "Successful Response", content = @Content( 
        mediaType = MediaType.APPLICATION_JSON, schema = @Schema(implementation = User.class) 
    )), 
    @APIResponse(responseCode = "404", description = "User not found")})
----

*4 . Request Parameter Definitions*  

* *`@Parameter`* - Describes request parameters. 

[source,  java]
----
@Parameter(description = "User ID", required = true)  
        @PathParam("id") String id) 
----

*5 . Schema Definitions*  

* *`@Schema`* at the `class level` provides metadata for the model.  

* *`@Schema`* at the `field level` describes each property of the model.  

[source,  java]
----
@Schema(description = "User model") 
class User { 
    @Schema(description = "Unique user ID", example = "123") 
    public String id; 
 
    @Schema(description = "User name", example = "John Doe") 
    public String name; 
----

These annotations play a crucial role in API development. They provide a clear, structured, and machine-readable way to define API behavior without requiring additional configuration files. These annotations allow developers to embed metadata directly into the code, ensuring that API endpoints, request parameters, response types, and security schemes are documented and consistent. 

Annotations make mpOpenAPI integration easier and allow for automatic creation of documentation that complies with OpenAPI. This not only improves developer productivity but also enhances API discoverability, making it easier for consumers to understand and interact with the API. With help of these annotations, teams can ensure that their APIs remain maintainable, scalable, and aligned with industry standards, reducing manual documentation efforts and minimizing discrepancies between implementation and documentation. 

== Influence  
As *API architectures evolve,* OpenAPI, the industry-standard specification for *documenting REST APIs,* is influencing how *GraphQL* and *gRPC* APIs handle documentation and interoperability. While OpenAPI was designed for REST, its structured approach to API documentation, tooling, and automation has influenced how GraphQL and gRPC handle documentation and interoperability. 

* OpenAPI’s structured *JSON/YAML format* has influenced *GraphQL’s SDL (Schema Definition Language),* where types, queries, and mutations are explicitly defined. 

* Inspired by OpenAPI's *Swagger UI*, gRPC now has *gRPC UI*, which allows developers to explore and test API methods interactively, much like Swagger does for REST APIs.   

== Conclusion  
In today's world of *microservices and cloud computing,* standardised API documentation is more important than ever. OpenAPI has become the foundation for creating *consistent, accessible, and well-documented APIs,* ensuring seamless integration across diverse systems. As APIs continue to evolve, having a structured approach to documentation helps developers *improve collaboration, reduce errors, and accelerate development cycles.* For those working with *Open Liberty,* exploring *mpOpenAPI* offers an effortless way to generate OpenAPI-compliant documentation, making API management more efficient. As we embrace automation and interoperability in modern software development, it would be hard to imagine _What would software development look like today if OpenAPI never existed?_
