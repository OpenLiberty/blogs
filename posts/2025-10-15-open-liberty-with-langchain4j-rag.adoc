Artificial Intelligence (AI) and generative AI have a profound impact on the economy and have introduced changes on how businesses operate. 
Generative AI use Large Language Models in order to generate words by using various probabilistic methods. 
Oftentimes these models are trained on out-dated information and sometimes the information provided during training is not specific to a particular domain and lacks specialized knowledge.
To solve this, an efficient and effective technique called Retrieval Augmented Generation (RAG) is used to provide relevant and up-to-date information.
The information that is used for RAG can be in several forms such as a website, vector database, or various images.
As a result, several forms of RAG exist such as multi-modal RAG which is RAG that works with different types of unstructured data such as text or images, or graph RAG that uses knowledge graph as the information source.

This post demonstrates how to construct a RAG application using LangChain4j to connect to the AI provider models, and store textual data inside a MongoDB Atlas database.
In this sample application, the local MongoDB Atlas is used but there are various ways to connect to the database such as connecting the database on the cloud using a connection string.

Furthermore, a vector database is used in this example. Vector databases have played an integral role to develop wide range of use cases such as natural language search, or even recommendation systems.
MongoDB Atlas vector database is equipped with unified data storage since the vector data and the operational data are in located in one place, efficient hybrid search mechanism which involves combining vector search with full-text search for metadata, and powerful aggregation pipelines.
Moreover, MongoDB Atlas scales vector search separately from the core database which increases performance for production heavy workloads.

[#what_is_RAG]
== What is RAG (Retrieval-Augmented Generation)? 

Retrieval-Augmented Generation (RAG) is an approach for the LLM to generate accurate and relevant information without the need to retrain the model which can become expensive and time-consuming. Without RAG, the LLM limits to general or out-dated information rather than showing relevant domain specific information. +

RAG can be thought of a two stage approach in this sample application. +

Stage 1. Initialization Stage: process and store the content as embeddings (vectors) inside the database. Each embedding corresponds to some text data. Oftentimes, the processing step involves chunking each piece of content into multiple text segments. +

Stage 2. Inference Stage: Upon the user query, convert the query to an embedding and then find similar embeddings. The query embedding and the database embeddings are compared; similar vectors are obtained from vector search and their respective content is obtained.
The similar content appended to the user query is now the augmented message sent to the AI.

Likewise, the sample RAG application consists of two parts: the OpenAPI UI where the API requests can be made to initialize the vector database and the chat application to interact with the LLM.

image::/img/blog/sample-langchain4j-rag-diagram.png[Diagram of How RAG Works,width=70%,align="center"] 

The vector search is then able to search relevant and domain-specific answers based on the context.
Vector search uses the semantic meaning of the data to perform the search rather than matching keywords as used in regular search based mechanisms. 

The sample application demonstrates:

* How to integrate LangChain4j with MicroProfile and Jakarta EE

* How to use MongoDB Atlas locally

* How to create OpenAPI UI and build a chat application

* How vector search works

=== Connecting to MongoDB Atlas

The docker-compose file is used to create a local containerized MongoDB Atlas database using the `mongodb/mongodb-atlas-local` image.
The database credentials are set inside the environment. Furthermore, the ports connect the host port to the container MongoDB port at 27017.

[source]
----
services:
  mongodb:
    image: mongodb/mongodb-atlas-local
    environment:
      - MONGODB_INITDB_ROOT_USERNAME= ...
      - MONGODB_INITDB_ROOT_PASSWORD= ...
    ports:
      - 27017:27017
----

Inside the https://github.com/OpenLiberty/sample-langchain4j/tree/main/rag-db/src/main/java/io/openliberty/sample/langchain4j/mongo[mongo] directory, MongoProducer.java file produces a MongoDatabase object that is used in other classes, and AtlasMongoDB.java file contains methods to create search indexes, retrieve similar content, remove, update, or delete the database contents.

See https://github.com/OpenLiberty/sample-langchain4j/blob/main/rag-db/src/main/java/io/openliberty/sample/langchain4j/mongo/MongoProducer.java[MongoProducer.java].
Various configuration property information are injected from the microprofile-config.properties. 

[source]
----
    @Inject
    @ConfigProperty(name = "mongo.dbname", defaultValue = "embeddingsdb")
    String dbName;

    @Inject
    @ConfigProperty(name = "mongo.user")
    String user;

    @Inject
    @ConfigProperty(name = "mongo.pass.encoded")
    String encodedPass;
----

The createMongo function decodes the password, and uses connection string in the form of: "mongodb://" +user + ":" + password + "@"+ hostname + ":" + port + "/" +dbName+ "?authSource=admin&directConnection=true" to produce a MongoClient object.
The MongoDatabase is produced by invoking the getDatabase(dbName) method on MongoClient and creates the database if the database with that name did not exist before.
The close method closes the connection.

[source]
----
@Produces
    public MongoClient createMongo(){
        String password = PasswordUtil.passwordDecode(encodedPass);
        return MongoClients.create(MongoClientSettings.builder()
                           .applyConnectionString(
                               new ConnectionString("mongodb://" +
                                   user + ":" + password + "@"+ hostname + ":" + port +
                                   "/" +dbName+ "?authSource=admin&directConnection=true"))
                           .build());
    }

    @Produces
    public MongoDatabase createDB(MongoClient client) {
        return client.getDatabase(dbName);
    }

    public void close(@Disposes MongoClient toClose) {
        toClose.close();
    }
----
This MongoDatabase will be used by other classes.

=== Building REST APIs to manage the vector database

The EmbeddingApplication.java and the EmbeddingService.java are used to build the REST APIs to manage the vector database.

The embedding application is created at `/api` in EmbeddingApplication.java. + 

See EmbeddingApplication.java
[source]
----
@ApplicationPath("/api")
public class EmbeddingApplication extends Application {

}
----

The EmbeddingService implements various REST API upon request at the application path `/embedding`.
The RolesAllowed defines which group is allowed to perform a particular request operation.
Similarly, the annotations such as APIResponses indicate the response code with the descriptions. +

Given the summary and content parameters, the `POST` request at `/api/embedding` stores the summary, content, and vector as a List<Float> together into MongoDB.

To accomplish this, a new BSON Document called newEmbedding is created with the key "Summary", and value as the summary itself. 
Likewise, for the vector, the value is calculated using the LangChain4j APIs. The modelBuilder.getEmbeddingModel() from ModelBuilder returns the EmbeddingModel.
The getEmbeddingModel() constructs the EmbeddingModel using respective embedding model names from the provider.
Calling the EmbeddingModel.embed(text) returns the Response<Embedding> object; to get the Embedding object form LangChain4j the content() method is called.
The actual vector is converted and stored as a List<Float> into MongoDB using the insertOne method.

See EmbeddingService.java
[source]
----
    @POST
    @Path("/")
    @Consumes(MediaType.APPLICATION_JSON)
    @Produces(MediaType.APPLICATION_JSON)
    @RolesAllowed({ "admin" })
    @APIResponses({
        @APIResponse(responseCode = "200", description = "Successfully added embedding."),
        @APIResponse(responseCode = "400", description = "Invalid embedding configuration.")})
    @Parameters(value = {
        @Parameter(
            name = "summary", in = ParameterIn.QUERY,
            description = "The summary of the embedding",
            required = true,
            schema = @Schema(type = SchemaType.STRING)),
        @Parameter(
            name = "content", in = ParameterIn.QUERY,
            description = "The content of the embedding",
            required = true,
            schema = @Schema(type = SchemaType.STRING))})
    @Operation(summary = "Add a new embedding to the database.")
    public Response add(
        @QueryParam("summary") String summary,
        @QueryParam("content") String content) {

        Document newEmbedding = new Document();
        newEmbedding.put("Summary", summary);
        newEmbedding.put("Content", content);
        newEmbedding.put("Vector",
            toFloat(modelBuilder.getEmbeddingModel().embed(content).content().vector()));
        mongoDB.insertOne(newEmbedding);

        return Response
            .status(Response.Status.OK)
            .entity(newEmbedding.toJson())
            .build();
    }
----

The `POST` request at `/api/embedding/init` works as follows to initialize the MongoDB database from the knowledge base. + 

If the database is empty, the search index is created using the methods as described in AtlasMongoDB. The code goes through the resources/knowledge_base files using the provided MD_FILES. Each line of the text file is extracted where the first line is stored as the summary, and the rest as the content. 
The summary, content, and embedding vector are created and added in the same document. Each document is inserted into MongoDB Atlas.

[source]
----
    @POST
    @Path("/init")
    @Consumes(MediaType.APPLICATION_JSON)
    @Produces(MediaType.TEXT_PLAIN)
    @RolesAllowed({ "admin" })
    ...
    public Response initializeDatabase() {
        if (mongoDB.isEmpty()) {
            mongoDB.createIndex();
            try {
                ClassLoader classLoader = EmbeddingService.class.getClassLoader();
                for (String txtFile : MD_FILES) {
                    InputStream inStream = classLoader.getResourceAsStream("knowledge_base/" + txtFile);
                    if (inStream != null) {
                        InputStreamReader reader = new InputStreamReader(inStream, StandardCharsets.UTF_8);
                        BufferedReader br = new BufferedReader(reader);
                        String summary = br.readLine();
                        StringBuffer content = new StringBuffer();
                        String line;
                        while ((line = br.readLine()) != null) {
                            content.append(line).append("\n");
                        }
                        br.close();
                        reader.close();
                        inStream.close();
                        Document newEmbedding = new Document();
                        newEmbedding.put("Summary", summary);
                        newEmbedding.put("Content", content.toString());
                        newEmbedding.put("Vector",
                                toFloat(modelBuilder.getEmbeddingModel().embed(summary).content().vector()));
                        mongoDB.insertOne(newEmbedding);
                    }
                }
                return Response.status(Status.OK)
                               .entity("Successfully loaded knowledge base into MongoDB.")
                               .build();
            } catch (Exception exception) {
                return Response.status(Status.INTERNAL_SERVER_ERROR)
                               .entity("Could not load knowledge base into MongoDB.")
                               .build();
            }

        }

        return Response
            .status(Response.Status.OK)
            .entity("Knowledge base already initialized.")
            .build();

    }
----

To understand how createIndex() method works, see the AtlasMongoDB.java.

Before the database is initialized in the program and for the vector search to work, createIndex() method generates a search index. 
A new collection is created within the existing MongoDatabase called EmbeddingsStored.Then, the createSearchIndexes method uses the information
such as the vector dimension of the embedding model, a cosine similarity approach, and the location inside the document where the vector is stored known as the path.

[source]
----    
    public void createIndex() {

        db.createCollection(COLLECTION_NAME);
        MongoCollection<Document> embeddingStore = db.getCollection(COLLECTION_NAME);

        Bson documentDefinition = new Document("fields",
            Collections.singletonList(
                new Document("type", "vector")
                    .append("path", PATH)
                    .append("numDimensions", modelBuilder.getEmbeddingModel().dimension())
                    .append("similarity", "cosine")));
        SearchIndexType vectorSearch = SearchIndexType.vectorSearch();
        List<SearchIndexModel> searchIndexModels = Collections.singletonList(
                new SearchIndexModel(SEARCH_INDEX_NAME, documentDefinition, vectorSearch));

        sleep(TIMEOUT);
		embeddingStore.createSearchIndexes(searchIndexModels);
        boolean indexReady = false;
        do {
            Document index = embeddingStore.listSearchIndexes().first();
            JSONObject json = new JSONObject(index.toJson());
            boolean queryable = json.getBoolean("queryable");
            if (queryable && json.getString("name").equals(SEARCH_INDEX_NAME)) {
                indexReady = true;
                break;
            }
        } while (!indexReady);
    }
----
The createSearchIndexes method is called to execute the request.

The search indexes are ready when queryable value is set to true and search indexes may take some time to become ready. +

In EmbeddingService.java, the `GET` request at `/api/embedding` lists the embeddings from the database using the retrieve method. It uses the mongoDB.getCollection().find() that returns all the Document objects from MongoDB. The MediaType.APPLICATION_JSON is returned. 

[source]
----
    @GET
    @Path("/")
    @Produces(MediaType.APPLICATION_JSON)
    @RolesAllowed({ "admin", "user" })
    @APIResponses({
        @APIResponse(responseCode = "200", description = "Successfully listed the embeddings."),
        @APIResponse(responseCode = "500", description = "Failed to list the embeddings.") })
    @Operation(summary = "List the embeddings from the database.")
    public Response retrieve() {
        
        StringWriter sb = new StringWriter();
        try {
            sb.append("[");
            boolean first = true;
            FindIterable<Document> docs = mongoDB.getCollection().find();
            for (Document d : docs) {
                if (!first) {
                    sb.append(",");
                } else {
                    first = false;
                }
                sb.append(d.toJson());
            }
            sb.append("]");
        } catch (Exception e) {
            return Response.status(Response.Status.INTERNAL_SERVER_ERROR)
                           .entity("[\"Unable to list embeddings: " + e.getMessage() + "\"]")
                           .build();
        }
        return Response.status(Response.Status.OK)
                       .entity(sb.toString())
                       .build();
    }
----

The `PUT` request below updates the existing content and summary given the object id at `/api/embedding/{id}`. 
A new document with summary, and content with its newly generated vector is created and replaced using replaceOne
for the existing object id (oid) located at _id. If none of the records match, a BAD_REQUEST status code is returned.

[source]
----
    @PUT
    @Path("/{id}")
    @Consumes(MediaType.APPLICATION_JSON)
    @Produces(MediaType.APPLICATION_JSON)
    @RolesAllowed({ "admin" })
    @APIResponses({
        @APIResponse(responseCode = "200", description = "Successfully updated embeddings."),
        @APIResponse(responseCode = "400", description = "Invalid object id or embeddings configuration."),
        @APIResponse(responseCode = "404", description = "Embeddings object id was not found.") })
    @Parameters(value = {
        @Parameter(
            name = "id", in = ParameterIn.PATH,
            description = "The object id of the embedding",
            required = true, example = "6880f9eef887c128f1ed0bf1",
            schema = @Schema(type = SchemaType.STRING)),
        @Parameter(
            name = "summary", in = ParameterIn.QUERY,
            description = "The summary of the embedding",
            required = true,
            schema = @Schema(type = SchemaType.STRING)),
        @Parameter(
            name = "content", in = ParameterIn.QUERY,
            description = "The content of the embedding",
            required = true,
            schema = @Schema(type = SchemaType.STRING))})
    @Operation(summary = "Update an embedding in the database.")
    public Response update(
        @PathParam("id") String id,
        @QueryParam("summary") String summary,
        @QueryParam("content") String content) {

        ObjectId oid;
        try {
            oid = new ObjectId(id);
        } catch (Exception e) {
            return Response.status(Response.Status.BAD_REQUEST)
                           .entity("[\"Invalid object id!\"]")
                           .build();
        }

        Document query = new Document("_id", oid);
        Document newEmbedding = new Document();
        newEmbedding.put("Summary", summary);
        newEmbedding.put("Content", content);
        newEmbedding.put("Vector", toFloat(
            modelBuilder.getEmbeddingModel().embed(summary).content().vector()));
        UpdateResult updateResult = mongoDB.replaceOne(query, newEmbedding);
        if (updateResult.getMatchedCount() == 0) {
            return Response.status(Response.Status.BAD_REQUEST)
                           .entity("[\"_id was not found!\"]")
                           .build();
        }

        newEmbedding.put("_id", oid);
        return Response.status(Response.Status.OK)
                       .entity(newEmbedding.toJson())
                       .build();
    }
----

Likewise, the `Delete` request at `/api/embedding/{id}` requires the object id to delete the particular document using the deleteOne method. The appropriate status code is returned. 

[#create_service]
=== Retrieving data from the vector database

In the first step, the user interacts with the RAG Chat Application.
The ChatService controls what happens upon any action on the http://localhost:9081/.

When a message is sent by the user, the `onMessage()` function is executed. 
The user query is converted to an embedding vector which is a List<Float>. 
Then the retrieveContent, method of AtlasMongoDB, performs the vector search and returns 
the text segments that are similar to the user query. 

The message is appended with these results and sent to the AI using the agent.chat(sessionId, message);

See ChatService.java
[source]

To dive deeper into how retrieveContent works, the AtlasMongoDB.java class should be explored.
See AtlasMongoDB.java. The role of the AtlasMongoDB.java class is to provide relevant functions for RAG such as creating search indexes, or retrieving similar content.
The MongoDatabase instance is injected. The ModelBuilder instance is required to get the corresponding embedding model; how the model builder creates the embedding model is explained in the later sections.
Note that the embedding model method called embed is used to convert text to embedding.

The database.getCollection method returns a MongoCollection<Document> which represents a collection of BSON documents.

----

The rest of the functions such as deleteOne, replaceOne and insertOne call the respective methods on the current collection.

The retrieveContent method takes in a userQuery embedding vector, and the query text. 
It uses the userQuery vector, the location or `PATH` to where the vectors are stored, selects `NUM_CANDIDATES` vectors in the nearby group in the latent space,
and returns the limit of `MAX_RESULTS_TO_AI`, based on the `SEARCH_INDEX_NAME`. The aggregate returns the results for $vectorSearch command and each result is a type of Document object.

[source]
----
    public List<String> retrieveContent(List<Float> userQuery, String query) {
        List<String> similarContent = new ArrayList<>();
        Document vecSearchDocument = new Document("queryVector", userQuery)
            .append("path", PATH)
            .append("numCandidates", NUM_CANDIDATES)
            .append("limit", MAX_RESULTS_TO_AI)
            .append("index", SEARCH_INDEX_NAME);
        Bson vectorSearch = new Document("$vectorSearch", vecSearchDocument);
        AggregateIterable<Document> results = getCollection().aggregate(Arrays.asList(vectorSearch));
        for (Document result : results) {
            similarContent.add(result.getString("Content"));
        }
        return similarContent;
    }
----

When BSON Documents are first stored by the sample application, each BSON Document contain 3 keys: "Summary", "Content", and "Vector". 
However, only the value of the "Content" section is required above and its value is obtained using result.getString("Content") for each result.  
It is important to note that the user message embedding is converted to a List<Float> since the vectors stored are also of type List<Float>.
