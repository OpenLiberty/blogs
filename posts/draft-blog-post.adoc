= Using Tools to perform tasks in your AI application
Andrew Sasmito <https://github.com/AndrewSasmito>

Recent advances in Artificial Intelligence (AI) have extended the capabilities of large language models (LLMs) through function-calling interfaces. Traditional LLMs generate responses based solely on pre-trained knowledge, making them ineffective for tasks requiring real-time data or external system interaction. Tool-calling capabilities address this limitation by allowing LLMs to invoke external functions, retrieve current information, and execute programmatic tasks. This mechanism enables LLMs to perform concrete actions through API calls and function execution rather than just generating text. For implementation details on tool-calling, see the https://www.ibm.com/think/topics/tool-calling[What is tool calling?] article from IBM.

This post demonstrates how to implement tool-calling capabilities in Java applications using the LangChain4j library, with a practical implementation in a Jakarta EE/MicroProfile application.

[#what_Are_LLMs_with_tools]
== What are tools for LLMs?

Tool-enabled LLM models can invoke external functions through standardized interfaces. When processing a prompt that requires capabilities beyond their internal knowledge or training data, these models can identify and call appropriate tools to fulfill the request. The tool-calling mechanism follows a specific protocol:

1. The LLM analyzes the user's request and determines if external tools are needed
2. If required, it generates a structured function call with appropriate parameters
3. The application executes the function with the provided parameters
4. The function returns results to the LLM
5. The LLM incorporates the returned data into its response

Several production-ready models including Llama 3.2, GPT-4.1, and Devstral implement tool-calling interfaces. These models are available through providers such as GitHub Copilot, Mistral AI, and Ollama, each with their own implementation specifications and capabilities.

[#Java_LLMs_Tools]
== Implementing tool-calling in Java applications

Implementing custom tool interfaces for LLMs requires significant development effort, particularly when supporting multiple model providers. The open source LangChain project provides abstraction layers that standardize tool interfaces across multiple LLM implementations, handling the complexities of different provider APIs.

For Java developers, https://github.com/langchain4j/langchain4j[LangChain4j] offers a comprehensive API that simplifies LLM integration. This library provides a consistent interface for tool definition, registration, and invocation across various AI platforms. With LangChain4j, you define Java methods as LLM-callable tools through annotations (`@Tool` and `@P`), enabling the framework to handle serialization, deserialization, and protocol management between your application logic and the AI model.

[#using_Langchain4j]
== Integrating LangChain4j with Jakarta EE and MicroProfile

LangChain4j integrates with enterprise Java applications built on Jakarta EE and MicroProfile specifications through standard dependency injection and configuration mechanisms. The library's components can be managed as CDI beans, configured through MicroProfile Config, and exposed via REST endpoints or WebSockets.

For basic implementation examples, refer to the https://github.com/langchain4j/langchain4j-examples[langchain4j-examples] repository. For more advanced features including streaming responses and tool integration patterns in an enterprise context, see the https://github.com/OpenLiberty/sample-langchain4j[sample-langchain4j] repository. This blog post specifically focuses on the tool-calling implementation demonstrated in the https://github.com/OpenLiberty/sample-langchain4j/tree/main/tools[sample-langchain4j/tools] directory.

[#how_app_work]
== How does the application work?

The application demonstrates the integration of several technologies:

* https://docs.langchain4j.dev/tutorials/tools[LangChain4j Tools] - For defining and managing LLM-callable functions
* https://openliberty.io/docs/ref/feature/cdi-4.0.html[Jakarta Contexts and Dependency Injection] - For dependency management and application scoping
* https://openliberty.io/docs/latest/reference/feature/websocket-2.1.html[Jakarta WebSocket] - For bidirectional client-server communication
* https://openliberty.io/docs/ref/feature/mpConfig-3.0.html[MicroProfile Config] - For externalized configuration of API keys and endpoints

LLMs are limited to information available in their training data, which becomes outdated and lacks real-time context. The tool-calling pattern addresses this limitation by enabling the LLM to request external data when needed.

In this sample application, the LLM is equipped with tools to query the https://stackoverflow.com[Stack Overflow] API. When the LLM determines that a user's question requires current information about programming issues or solutions not covered in its training data, it invokes the appropriate tool method. The implementation follows this sequence:

1. The tool searches for relevant questions using the https://api.stackexchange.com/docs/excerpt-search[StackExchange excerpt-search API]
2. For matching questions with answers, it retrieves the top-voted answer using a separate API call
3. The tool returns structured data (question ID, question text, and answer) to the LLM
4. The LLM processes this information and generates a comprehensive response that incorporates both its general knowledge and the specific Stack Overflow content

This architecture demonstrates how to extend an LLM's capabilities through programmatic API integration while maintaining a clean separation of concerns.

[#create_tool]
=== Creating the tools

To create functions that the LLM can call, methods must be annotated with `@Tool` and include a descriptive string that helps the AI model understand the tool's purpose and usage context. For method parameters, the `@P` annotation provides semantic information that guides the LLM in supplying appropriate arguments. These annotations are critical for the LLM to:

1. Determine when a particular tool is appropriate for a given user query
2. Construct valid parameter values based on the query context
3. Understand the expected return type and how to incorporate it into responses

The `searchStackOverFlow` tool implements HTTP client calls to the https://api.stackexchange.com/[Stack Exchange API] using Jakarta REST Client. The implementation includes error handling, response parsing, and data transformation to provide structured results to the LLM. The example below shows one of the tool methods:

See the {example-location}/src/main/java/io/openliberty/sample/langchain4j/StackOverflowTools.java[src/main/java/io/openliberty/sample/langchain4j/StackOverflowTools.java] file to learn more.
[source, java, role="no_copy"]
----
public class StackOverflowTools {
    ...
    private ArrayList<String> questionAndAnswer(String url) throws Exception {
        ArrayList <String> questionAnswer = new ArrayList<>();
        for (Map<String, Object> data : clientSearch(url)) {
            String topAnswer = clientSearch(String.format(findAnswer, data.get("question_id")))
                                    .get(0).get("body").toString();
            questionAnswer.add(
                "Link: " + "https://stackoverflow.com/questions/" + data.get("question_id") + 
                " Problem: " + data.get("body") +
                " Answer: " + topAnswer
            );
        }
        return questionAnswer;
    }
    ...
    @Tool("Search for questions and answers on stackoverflow")
    public ArrayList <String> searchStackOverflow(@P("Question you are searching") String question) throws Exception {
        logger.info("AI called the searchStackOverflow Tool with question: " + question);
        String targetUrl = stackOverflowMethod + "&q=" + question;
        return questionAndAnswer(targetUrl);
    }
}
----

[#create_service]
=== Creating the LangChain4j AI service

The application uses CDI to inject a https://github.com/OpenLiberty/sample-langchain4j/blob/3564a2f12e4caea7f2ce627d337d2647eafa5d0e/tools/src/main/java/io/openliberty/sample/langchain4j/ChatAgent.java#L33-L34[StackOverFlowTools] instance into the AI service. The service is then configured using the builder pattern, with several important components:

1. The `ChatModel` implementation, which is dynamically selected based on environment configuration
2. The tool instances registered via the https://github.com/OpenLiberty/sample-langchain4j/blob/3564a2f12e4caea7f2ce627d337d2647eafa5d0e/tools/src/main/java/io/openliberty/sample/langchain4j/ChatAgent.java#L58[tools] parameter
3. A https://github.com/OpenLiberty/sample-langchain4j/blob/3564a2f12e4caea7f2ce627d337d2647eafa5d0e/tools/src/main/java/io/openliberty/sample/langchain4j/ChatAgent.java#L59[hallucinatedToolNameStrategy] to handle cases where the LLM attempts to call non-existent tools

The `hallucinatedToolNameStrategy` is particularly important for robust error handling. When an LLM attempts to call a tool that doesn't exist (a common issue with some models), this strategy returns a structured error message that informs the model of the invalid tool name. This feedback mechanism allows the LLM to recover and potentially select a different, valid tool instead.

See the {example-location}/src/main/java/io/openliberty/sample/langchain4j/ChatAgent.java[src/main/java/io/openliberty/sample/langchain4j/ChatAgent.java] file.
[source, java, role="no_copy"]
----
    public Assistant getAssistant() {
        ...
            ChatModel model = modelBuilder.getChatModel();
            assistant = AiServices.builder(Assistant.class)
                .chatModel(model)
                .tools(stackOverflowTools)
                .hallucinatedToolNameStrategy(toolExecutionRequest -> ToolExecutionResultMessage.from(
                    toolExecutionRequest, "Error: there is no tool with the following parameters called " + toolExecutionRequest.name()))
                .chatMemoryProvider(
                    sessionId -> MessageWindowChatMemory.withMaxMessages(MAX_MESSAGES))
                .build();
       ...
    }
----

The service implementation uses a Java interface with LangChain4j annotations to define the interaction contract with the LLM. Through this customized `Assistant` interface, the application sends messages to the LLM via the `chat()` method. The interface includes a `@SystemMessage` annotation that provides critical context to the LLM about its role, available tools, and expected behavior.

See the {example-location}/src/main/java/io/openliberty/sample/langchain4j/ChatAgent.java[src/main/java/io/openliberty/sample/langchain4j/ChatAgent.java] file.
[source, java, role="no_copy"]
----
    interface Assistant {
        @SystemMessage("You are a coding helper, people will go to you for questions around coding. " +
            "You have ONLY four tools. " +
            "ONLY use the tools if NECESSARY. " +
            "ALWAYS follow the tool call parameters exactly and make sure to provide ALL necessary parameters. " +
            "Do NOT add more parameters than needed" + 
            "NEVER give the user unnecessary information. " + 
            "NEVER lie or make information up, if you are unsure say so.")
        String chat(@MemoryId String sessionId, @UserMessage String userMessage);
    }
----

[#communicate]
=== Communicating between the client and LLM

The application implements a WebSocket-based communication architecture for real-time interaction between the client and the LLM. Jakarta WebSocket provides the bidirectional communication channel between the browser client and the `ChatService` endpoint. Each client establishes a persistent WebSocket connection to the service endpoint and transmits messages using the standard WebSocket `send()` method.

See the {example-location}/src/main/webapp/toolChat.js[src/main/webapp/toolChat.js] file.
[source, java, role="no_copy"]
----

    const webSocket = new WebSocket(uri);
    ...
    function sendMessage() {
        ...
        var myMessage = document.getElementById('myMessage').value;
        ...
        webSocket.send(myMessage);
        ...
    }
----

On the server side, the `ChatService` class is annotated with `@ServerEndpoint` to handle WebSocket connections. It receives user messages through the `@OnMessage`-annotated method, maintains session state for each client, forwards requests to the LLM through the `ChatAgent.chat()` method, and transmits responses back to the client using the WebSocket `sendObject()` method. This architecture enables low-latency, stateful communication while maintaining clean separation between the presentation layer and the AI service implementation.

See the {example-location}/src/main/java/io/openliberty/sample/langchain4j/ChatService.java[src/main/java/io/openliberty/sample/langchain4j/ChatService.java] file.
[source, java, role="no_copy"]
----

    @OnMessage
    public void onMessage(String message, Session session) {
        ...
        try {
            ...
            answer = agent.chat(sessionId, message);
        } catch (Exception e) {
            ...
        }

        try {
            session.getBasicRemote().sendObject(answer);
        } catch (Exception e) {
            e.printStackTrace();
        }

    }
----
